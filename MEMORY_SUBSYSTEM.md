# Per-User Memory Subsystem — Design Notes

**Started:** 2026-05-12
**Project:** liveavatar-advisor
**Status:** Design selected. No code written yet.

This is a living document. Add a dated entry at the bottom whenever the
design shifts materially.

---

## What we're building

A per-user memory layer for the live-avatar financial-advisor product.

The avatar identity (Tom Olds persona, system prompt, voice, face) is
**fixed at the project level** — the same advisor for every visitor.

The conversational memory is **per-user**. Each visitor has a folder.
When they return, the avatar pulls up their profile + a synthesized
summary of past sessions and picks up the conversation rather than
starting cold.

This is the AI-native equivalent of a financial-advisor CRM — built into
the product instead of bolted on after the fact.

---

## The architecture we're adopting

Direct port of the **openclaw markdown-memory pattern**, scoped per-user.

```
liveavatar-advisor/
└── users/
    └── <user_id>/
        ├── USER.md          ← canonical profile (durable facts)
        ├── memory/
        │   ├── 2026-05-12_15-00.md   ← raw session log
        │   ├── 2026-05-13_10-30.md
        │   └── ...
        └── MEMORY.md        ← compiled wiki, regenerated from memory/
```

Three discipline lines we inherit from openclaw:

1. **Durable vs. dated.** `USER.md` holds preferences, working style,
   relationships, recurring patterns — things that age slowly.
   `memory/*.md` holds dated facts: specific questions, decisions, the
   text of a conversation. Specific projects retire when they're done;
   their lasting takeaway folds back into the durable layer.
2. **Raw vs. compiled.** `memory/*.md` is writable; `MEMORY.md` is a
   synthesized wiki regenerated by a compiler pass. Compiled file
   carries a "DO NOT EDIT MANUALLY" header so the boundary stays
   visible.
3. **Consolidate periodically.** A reflective pass (the
   `consolidate-memory` skill in openclaw) merges duplicates, fixes
   stale facts, converts "next week" into absolute dates, and prunes
   the index back to ~200 lines / ~25 KB.

## Session lifecycle

| Moment            | What happens                                                 |
|-------------------|--------------------------------------------------------------|
| Session start     | Backend reads `users/<id>/USER.md` + `MEMORY.md`, injects both into the system prompt for the LLM call. |
| During session    | Hot turn state stays in memory exactly as today. No change.  |
| Session end       | Async write of `users/<id>/memory/<timestamp>.md` digesting the conversation: Context, Key Insights, Decisions, Open Questions. |
| Periodically      | `memory_compiler.py` regenerates `users/<id>/MEMORY.md` from the raw logs. |
| Less often        | Consolidate pass retires dated content and sharpens durable. |

## Phasing

**Phase 1 — local Mac (where we are now)**
- Cookie UUID for identity (anonymous, claim-later flow comes in Phase 1.5)
- Markdown files on disk under `users/`
- New helpers in `advisor_backend.py`: `load_user_context()`,
  `save_session_digest()`
- One small `memory_compiler.py` script that mirrors the openclaw one,
  scoped per-user

**Phase 2 — AWS serverless**
- `users/<id>/` becomes either an S3 prefix or a DynamoDB single-table
  layout (partition key `user_id`, sort key `kind#timestamp`)
- Markdown content stays the same; only the storage substrate changes
- Compiler moves to a Lambda triggered by a `sessionEnd` event

**Phase 3 — semantic memory** *(only if needed)*
- ChromaDB or pgvector for clients with months of session history
- Probably never necessary if the markdown digest + compiler stays
  fresh. Don't build until the warm-store profile + summary stops
  being enough.

## Open design questions

**Identity.** Cookie UUID is fine for the demo but not for production.
Decide: magic-link email (soft identity) vs. proper auth like Cognito
(hard identity). Either way needs to land before the avatar is shown to
strangers, because the moment a real prospect uses it, regulatory
expectations attach.

**Consent and retention.** Regulated industry, financial information.
Right-to-rectification maps cleanly onto the markdown pattern — the
user can read their own `USER.md` and ask for corrections. Right-to-be-
forgotten maps onto `rm -rf users/<id>/`. Consent capture on first visit
needs to exist before this leaves the personal-demo phase.

**Supervisor view.** Eventually you (Tom-the-human) will want a page
showing the last N conversations across all clients, to spot-check what
your digital twin has been telling people. Not v1, but the markdown
content should stay human-readable so this is a thin UI layer when we
add it.

**The "not a dossier" line.** openclaw's USER.md template carries this
caveat: *"you're learning about a person, not building a dossier.
Respect the difference."* Worth preserving the spirit. In a regulated
financial context the implementation has to match the rhetoric: small,
durable fact set, not a behavioral profile.

## Reference: openclaw's memory files

If you ever want to look at the source of the pattern:

```
~/.openclaw/workspace/
├── USER.md                            ← template (name, what to call, notes)
├── IDENTITY.md                        ← agent persona (we don't port this)
├── MEMORY.md                          ← compiled wiki
├── memory/YYYY-MM-DD.md               ← raw daily logs
└── memory_compiler.py                 ← LLM synthesis script

~/.claude/skills/consolidate-memory/
└── SKILL.md                           ← reflective-pass procedure
```

The line worth re-reading every time:

> Separate the durable from the dated. Preferences, working style, key
> relationships, and recurring workflows are durable — keep and sharpen
> them. Specific projects, deadlines, and one-off tasks are dated — if
> the date has passed or the work is done, retire the file or fold the
> lasting takeaway into a durable one.

- **2026-05-22** — Defensive templated greeting on silent tool-call
  (task #71). Diagnosed from live testing where Tom heard only the
  first response in his second session — the new `save_client_profile`
  tool fired with no spoken text from the LLM (standard OpenAI
  function-calling pattern), leaving the avatar mute on the
  introduction turn. Mirrors the calculator's
  `_calculator_response_template` pattern: when
  `save_client_profile` fires AND `full_reply` is empty AND a name
  was captured, stream a short templated greeting through ElevenLabs
  so the avatar always says something. Distinguishes first-
  introduction ("Got it, Frank — welcome. What's on your mind
  today?") from explicit-correction ("Got it — I'll call you Mike
  from here.") based on whether USER.md existed before the tool
  ran. Three-branch behavioral test (silent → backstop fires, chatty
  → backstop stays out, correction → short ack) passes. No
  regression on the chatty-LLM happy path.
- **2026-05-17** — Auto-compile after digest (task #65). The previous
  design followed openclaw literally: digests written per-session, but
  `MEMORY.md` only regenerated when the user explicitly ran
  `scripts/compile_memory.py`. Found in live testing that this leaves
  early-stage clients with empty `MEMORY.md` and therefore no
  conversational continuity beyond what's in `USER.md` — the avatar
  knew Jack's name on visit 2 but not the $750k SPIA quote we'd just
  worked through. Fix: `save_session_digest()` now `await`s a new
  `compile_user_memory()` after writing each digest. Same fire-and-
  forget chain (the whole save_session_digest is already a background
  task). Adds one LLM call per session (~$0.005) but means session 2
  inherits everything from session 1 with zero manual steps.
  Compiled file gets an `(auto-compiled by backend)` marker in the
  header so it's visually distinguishable from CLI-compiled output.
  `scripts/compile_memory.py` is now mostly useful for batch
  recompiles, manual debugging, or after USER.md / digests have been
  hand-edited and the model should resynthesize. Behavioral test
  (mocked aclient + temp users dir) confirms: digest writes,
  MEMORY.md writes, both LLM calls fire in correct order,
  load_user_context returns the new CLIENT CONTEXT block for the
  next session. Anonymous and no-digest paths short-circuit safely.
- **2026-05-16 (still later)** — Structured access logging shipped
  (task #64) ahead of the first live test. FastAPI `@app.middleware`
  writes a JSON line per request to `logs/access.jsonl` with:
  timestamp (UTC, ms precision), client IP (X-Forwarded-For aware),
  user_id from the cookie, method, path, status, elapsed_ms, and
  truncated user-agent. Rotating handler caps at 10MB × 5 files.
  `run.sh` updated with `--proxy-headers --forwarded-allow-ips='*'`
  so ngrok-forwarded IPs reach the app. `logs/` added to `.gitignore`
  (IP addresses are personal data; never commit). Streaming endpoints
  measure time-to-first-byte, not full streaming duration — known
  quirk, documented in the middleware comment. Behavioral smoke test
  via FastAPI's TestClient: 5 branches (anonymous, set-cookie, with-
  cookie, XFF, 404) all log correctly with all expected fields.
- **2026-05-16 (later)** — Phase 1 identity-bootstrap shipped (task
  #60). `save_user_profile()` writes `users/<id>/USER.md` with name +
  optional notes, preserving `first_met` on re-saves.
  `save_client_profile` registered as an LLM tool with a description
  that limits firing to first-introduction or explicit-correction only.
  `_run_tool` threads `user_id` through. `/api/llm` and
  `/api/converse-stream` both pass it. The streaming endpoint runs

  streamed its greeting in the same turn — no templated response
  needed, unlike the calculator). `load_user_context()` returns a new
  FIRST VISIT instruction block when the user folder is empty,
  directing the avatar to greet warmly, ask the name, and call the
  tool. Behavioral smoke test (9 branches) passes: anonymous
  rejection, name validation, USER.md creation, notes section,
  idempotent re-save, CLIENT CONTEXT transition, tool dispatch.
  Phase 1 is functionally complete; the working tree now does the
  full read-on-start / write-on-end / compile-periodically cycle.
- **2026-05-16** — `scripts/compile_memory.py` shipped (task #59).
  Per-user compiler mirroring the openclaw pattern: reads every
  `users/<id>/memory/*.md`, calls the LLM with a synthesis prompt
  tuned for an advisor-CRM-style wiki (Snapshot / Profile /
  Conversation history / Active questions / Recommendations on file),
  writes `users/<id>/MEMORY.md` with a "do not edit manually" header.
  Idempotent: skips users whose `MEMORY.md` is newer than all their
  digests; `--force` overrides. `--dry-run` for inspection. `--user <id>`
  for single-user runs. Input capped at 80k chars with head+tail
  truncation when needed. Dry-run smoke test against synthetic user
  folders passes all branches (compile, skip-up-to-date, skip-empty,
  force, truncate). The backend's `load_user_context()` already reads
  `MEMORY.md` whenever it exists, so the compiler's output is
  automatically picked up on the next session. Cadence is manual for
  now (Tom invokes after sessions or on a daily cron); a scheduled-
  task version is a natural follow-up. Next: first-visit identity
  flow (#60).
